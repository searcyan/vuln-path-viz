# 从源码和证据，推到一张图

顺序不能反过来：**先有证据，再画图**。反过来会得到一张漂亮但站不住的图。

## 0. 先定「一条路径 + 一个 impact」

写下来两句话，再动手：

```
入口：POST /config/update   （普通虚拟 key，Authorization: Bearer sk-…）
终点：GET /get_image 返回 /etc/shadow 内容   （实测 801 字节）
```

终点必须是**可观测的具体后果**：读到了某个文件、密钥出现在攻击者服务器日志里、返回了 200 且数据库里字段变了。没有 impact 的路径不画。

## 1. 拿真实行号（最容易被偷懒毁掉的一步）

- 解包与阅读的版本要写死（如 `someapp==1.2.3` 的 wheel），并保留源码目录供读者对照。
- 每条卡片行都从文件里 `grep`/读出来，复制原文，不要誊写。
- 一次请求只覆盖一条栈；用 `curl`/PoC 打出实测输出（状态码、响应体、字节数）作为终点证据。
- 有运行时轨迹更好（`sys.settrace`、框架的 debug trace、debugger 断点日志）：它证明"我以为的跳转"真的发生，也能抓出你没读到的中间调用。把轨迹落成一份 `trace.md`，图里每个跳转都能对上其中一行。
- 收尾时给卡片加 `src` 字段并跑 `lint-scene.mjs --src-root`：它会回到源码逐行比对，行号漂移或代码誊错会直接报 error。

## 2. 决定卡片粒度

一句话规则：**一个卡片 = 读者会问"这是谁"的最小单位 = 一个函数**。

| 情况 | 处理 |
|---|---|
| 函数只有 1~3 行且无分支（如 `get_api_key` 剥 Bearer） | 仍给一张卡，但只列关键行；它是读者会问"这谁"的对象 |
| 框架内部/无关紧要的一层（如 `Router.acompletion` 的包装） | 压成一句话写进上一步的 `text`，不单独成卡 |
| 同一函数在不同阶段多次进入 | 只保留一张卡，用多个 step 在不同行上停留 |
| 跨了另一个 HTTP 请求 | 新卡片 + `tag:"另一个请求"`，边用 `dashed:true` |
| 背景/请求/响应/时序/复盘 | `kind:"term"` |

卡片数量目标 8~18 张。超了：把"顺路经过但不影响结论"的卡片降级为正文一句话。

## 3. 定 depth（调用栈深度）

```
proxy 路由 handler        → 0
鉴权入口（Depends 调用的）  → 1
  它调用的 builder         → 2
    builder 调的检查函数     → 3
      检查函数调的子函数      → 4
```

- depth = **列**。兄弟函数同 depth 会上下排在同一列，视觉上"并列"，这正是想表达的语义。
- 若某条链深到 7 列以上，中间层压成一句话，别把画布拉到 8 列宽。
- term 卡（背景/请求）放在 depth 0 顶部；响应卡放在拒绝路径末端；复盘卡放在最深列或 0 列末尾均可（它是"旁白"，不参与调用链）。

## 4. 铺边

按执行顺序走一遍，每次函数调用画一条边，标 `at` 行号。分叉时**两条边都画**：

```js
{ from:"allowed_route", at:693, to:"api_route_allowed", path:"bad"  },   // 普通 key 走这条 → 401
{ from:"allowed_route", at:690, to:"is_ui_route",      path:"ok"   },   // ui key 走这条 → 200
```

然后回到起点，把拒绝路径和通过路径**各走一遍**写成 steps：先走完拒绝（读者先看到"本该拦住"），再走通过（读者看到"为什么没拦住"）。这个顺序比反过来有力得多。

## 5. 写步（steps）

- 第一步 `⓪ 背景`：讲清这个系统里有哪些角色、哪些接口、攻击者手里有什么。**没有这一步，后面全是术语**。
- 第二步：真实的 `curl`（脱敏成 `TARGET` / `TOKEN` 占位）。
- 中间：每次函数调用 + 每次返回各一步；返回用 `via:{…,ret:true}`。同一函数内连续推进可以连着几步不带 `via`。
- 分叉点单独一步，用 `warn` 徽标，把判断条件原样念出来（类如 `token_type = "ui" if team_id == "<dashboard-team>" else "api"`）。
- 落点（写 `os.environ`、发 `Authorization`、`FileResponse`）用 `bad` 徽标，并给出实测证据。
- 最后：复盘卡。

## 6. 证据分级（在正文与文档里都要标）

| 级别 | 含义 | 写法 |
|---|---|---|
| 实测 | 真的打出来了，有输出/日志/字节数 | 「实测 801 字节」「响应 200，body 里含 …」 |
| 代码级 | 读源码可确定，没实跑 | 「代码级：路由判断用的是前缀匹配」 |
| 推断 | 合理但未验证 | 「推断：若 …… 则会 ……」 |

图里可以混用，但**不能把推断写成实测**。交付说明里给一张证据台账（哪几步是实测、哪几步是代码级）。

## 7. 交付前抽检

- `lint-scene.mjs --src-root` 零 error：它已经在替你逐行比对源码
- 再随机抽 3 张卡片，打开源码看一眼上下文（确认这几行确实属于这条路径，而不只是字面一致）
- 从第一步按到末步，每步都能回答：我从哪来（`via`）、现在在哪（高亮行）、下一步去哪（出边）
- 拒绝路径与通过路径的颜色没串；两条路径的差异点在图上能一眼指出（通常是同一个"分叉点"卡片的两行）
- `lint-scene.mjs` 的 warn 每条都有理由
- 无头截图 2~3 步（含分叉点、含复盘卡）看版式

## 8. 与文档的分工

讲解页负责**让人看懂一条路径**；文字文档负责**可检索、可引用**（行号清单、命令、对照表）。

所以：页面先做（它逼你把路径走通），然后写一份同路径的 markdown（便于 grep 和引用），最后才是长文分析。三者出现不一致时，**以实测输出为准**，其次以源码为准 —— 图必须跟着改。
